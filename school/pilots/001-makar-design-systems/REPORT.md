# Pilot 001 — Makar Design Systems

## Purpose

This is the first end-to-end validation of **ALINA School**, not another frontend milestone.

We take one graduate competency and connect:

```text
competency
→ skills
→ knowledge/patterns
→ lessons/labs/project
→ assessments
→ real evidence
→ mastery proposals
→ adaptive path
```

## What exists now

The Design Systems competency has been decomposed into eight target K4 skills:

1. semantic token architecture;
2. reusable UI primitives;
3. theme separation;
4. accessibility states;
5. responsive component behavior;
6. reduced-motion behavior;
7. visual/system consistency;
8. component API boundaries.

The graph also includes prerequisite knowledge, patterns, anti-patterns, lessons, labs, a project and an assessment.

## Real evidence used

Only evidence already present in the repository was mapped:

- PR #2 — Design Tokens foundation;
- PR #8 — UI Primitives + Visual Token Lab;
- successful CI run 35921883245 for PR #8.

No reading history was treated as practical mastery.

## Conservative diagnostic

Before school review, only the previously explicit Makar skill state is accepted automatically:

- semantic tokens: K3;
- UI primitives: K3.

The other newly decomposed skills remain unpromoted even where strong PR evidence exists.

Therefore the current checkpoint readiness is approximately **20.36%**.

That low number is intentional: the school does not rewrite the student record just because it discovered evidence.

## Evidence-backed proposals

The existing work supports eight reviewable K4 proposals.

Every proposal has:

- source evidence;
- demonstrated capability;
- independent/not-independent flag;
- strength;
- review required.

**Nothing is auto-promoted.**

## Adaptive path

Before review:

- known K3 skills receive a **shortened** path toward K4;
- unconfirmed skills/knowledge remain **full**;
- after evidence review, the path must be regenerated.

This is the first important school behavior:

> The curriculum changes after diagnosis, but diagnosis itself remains evidence-driven and reviewable.

## Important discovery

A project can prove a practical skill without automatically proving every prerequisite knowledge node.

For example, a good token implementation is strong evidence of applied design-system skill, but ALINA School should not silently mark every underlying concept as mastered.

This separation lets us ask precise questions:

- does Makar know it?
- can Makar do it?
- what proves that?
- how confident are we?
- what still needs assessment?
